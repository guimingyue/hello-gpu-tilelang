# 第 4 课 Tile、索引与尾部保护

> 上一课跑通了十个数的加法。本课回答当时留下的两个问题：为什么是 3 个线程组？为什么有 2 个位置要跳过？学完你能对任意长度手算分工，并解释少写一个 `if` 会发生什么。

## 4.1 Tile 是“一块数据”，不是硬件

**Tile（块）是程序处理的一块数据**；线程组（threadgroup）是执行工作的一组线程。两者不是一回事：一个线程组可以处理一个 tile，也可以处理多个；tile 多大、线程多少，是程序与编译器共同决定的映射。

第 3 课的设置是：每块 4 个元素，每组 32 个线程。块大小**不必等于**线程数——编译器会把 4 个逻辑迭代映射到 32 个线程中的前几个（或做其他合法映射），多余的线程在这个 kernel 里没有有效工作。教学设置故意小，方便观察；性能设置是第 10 课与实战篇的事。

## 4.2 手算分工

长度 `n=10`，块大小 `block=4`：

```text
组数 = ceil(10 / 4) = 3          ← T.ceildiv(n, block)
组 0：候选索引 0, 1, 2, 3        ← 全部有效
组 1：候选索引 4, 5, 6, 7        ← 全部有效
组 2：候选索引 8, 9, 10, 11      ← 10、11 越界，必须跳过
```

索引公式 `idx = bx * block + i`：`bx` 是组号，`i` 是块内逻辑迭代号。组 2 的 `i=2` 给出 `idx=10`——数组只有 0–9，这就是尾部。

**为什么用向上取整而不是向下？** 向下取整 `10//4=2` 组只覆盖 8 个元素，最后两个永远没人算。向上取整保证覆盖，代价是最后一组可能有多余候选位置，用 `if idx < n` 挡掉。

## 4.5 去掉保护会怎样

不要真的删掉 `if` 去跑——越界读写是未定义行为，可能崩溃、可能污染别的内存、也可能“看起来正常”。正确的心智是：

- 候选位置 `idx ≥ n` 时，`A[idx]` 根本不存在；
- GPU 不会替你检查数组边界；
- 所以保护必须在**访问之前**，而不是“算完再判断要不要写”。

第 6 课会见到另一种尾部策略：**主机补零**，让设备端无条件读取合法位置。两种策略各有适用场景，不是谁取代谁。

## 4.6 T.Parallel 到底声明了什么

`for i in T.Parallel(block)` 声明的是**可并行的逻辑迭代**，不是“开 block 个线程”。编译器负责把它映射到线程组的执行资源：可能一线程一迭代，也可能向量化、合并。第 10 课打印生成代码时你会看到：本课 block=128、threads=32 的加法被编译成每线程处理 4 个连续元素的 `float4` 运算。

现在只需记住：**你声明意图，编译器决定映射；映射是否高效，要测量才知道。**

## 4.7 练习与自检

1. `n=100, block=32`：几组？跳过几个？最后一组的有效索引范围？
2. 为什么 `threads=32` 而 `block=4` 是合法设置？多余线程在做什么？
3. 把 `T.ceildiv` 换成 `n // block`，`n=10, block=4` 时输出会怎样？

<details>
<summary>参考答案</summary>

1. `ceil(100/32)=4` 组，候选 128，跳过 28；最后一组有效索引 96–99。
2. 合法：逻辑迭代数与线程数解耦，编译器做映射；多余线程没有有效迭代，不写输出。
3. 只启动 2 组，索引 8、9 无人计算，输出对应位置保持初始值（本脚本填 NaN，断言会失败）。

</details>

**本课带走：** tile 是数据分块，线程组是执行单位；`ceildiv` 保证覆盖，`if idx < n` 保证安全。下一课看 kernel 里的条件与循环怎样表达“每个元素自己的故事”。
