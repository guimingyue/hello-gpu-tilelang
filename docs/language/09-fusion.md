# 第 9 课 融合：少写一次中间结果

> 本课的问题：`relu(a + b)` 可以写成两个 kernel（先加、再 ReLU），也可以写成一个。两种写法结果相同，但设备要做的事不同。理解这个差别，就理解了实战篇 Attention/RMSNorm 章节的核心动机。

## 9.1 两版写法，同一数学

**分离版**（两次启动 + 一个中间张量）：

```python
make_add(n, 32)(a, b, temporary)   # kernel 1：temporary = a + b
make_relu(n)(temporary, separate)  # kernel 2：separate = max(temporary, 0)
```

**融合版**（一次启动，无中间张量）：

```python
with T.Kernel(T.ceildiv(n, block), threads=32) as bx:
    for i in T.Parallel(block):
        idx = bx * block + i
        if idx < n:
            C[idx] = T.max(A[idx] + B[idx], 0)   # 加完立刻 ReLU
```

融合版里 `A[idx] + B[idx]` 的结果只存在于寄存器，从未写回全局内存。**省掉的是中间张量的一写一读，以及一次 kernel 启动的提交开销。**

## 9.3 融合省了什么，没省什么

| 项目 | 分离版 | 融合版 |
| --- | --- | --- |
| kernel 启动次数 | 2 | 1 |
| 中间张量全局读写 | 写 n + 读 n 个元素 | 0 |
| 算术运算量 | 相同 | 相同 |
| 输入读 / 输出写 | 相同 | 相同 |

注意**算术量没变**：融合不是“少算了”，是“少搬了”。对访存受限的算子（逐元素、归一化）这往往是大头；对计算受限的算子（大矩阵乘）收益可能很小。

还有一个容易忽略的收益：分离版的中间张量要**分配内存**，融合版不需要。小算子串联时，分配与启动开销可能比计算本身还大。

## 9.4 融合的边界：不保证更快

本课没有计时，所以**不能**说“融合版更快”。事实上本仓库第 12 章的实测里，教学版 Attention 的在线融合与物化三阶段墙钟几乎相同——融合收益取决于中间量大小、占用率与后端实现。正确的态度是：

1. 融合改变的是**数据流**（少写中间量），不是数学；
2. 是否更快，由第 10 课的方法测量；
3. 融合也会增加单个 kernel 的复杂度（寄存器压力、分支），有时反而慢。

## 9.5 改一个条件

把融合版的 `T.max(..., 0)` 改成 `T.max(..., 1)`（相当于 clamp 下界为 1），先预测输出再跑：`[1,1,1,1,6]`。再试着在融合版里加第三步 `* 2`，确认只需改一行表达式——这就是融合的表达力：**逐元素链条想接多长接多长，中间量都不落地**。

## 9.6 练习与自检

1. 融合版省掉的“一写一读”发生在哪两级存储之间？
2. 为什么大矩阵乘后面接一个 ReLU，融合收益通常比例元素链条小？
3. 两版结果一致，能推出两版耗时一致吗？

<details>
<summary>参考答案</summary>

1. 全局内存（device 缓冲）与寄存器之间：分离版中间结果写回全局再读入，融合版留在寄存器。
2. 矩阵乘本身计算量大、计算受限，中间量读写占比小；逐元素算子计算轻、访存占比大。
3. 不能。正确性与性能是两件事，必须分别验证与测量。

</details>

**本课带走：** 融合 = 把逐元素链条合进一个 kernel，省中间量读写与启动；收益要测，不保证。下一课正式学测量，并看看编译器到底生成了什么。
