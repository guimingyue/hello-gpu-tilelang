# 第 8 课 从点积到分块矩阵乘

> 矩阵乘是 GPU 编程的“成人礼”：它把前面所有概念——索引、分块、共享内存、累加器、同步——一次性用上。本课从手算 2×2 开始，到运行一个真正的分块 kernel。

## 8.1 手算：一个输出元素是一个点积

```text
A = [[1, 2],     B = [[5, 6],
     [3, 4]]          [7, 8]]

C[0,0] = 1·5 + 2·7 = 19     C[0,1] = 1·6 + 2·8 = 22
C[1,0] = 3·5 + 4·7 = 43     C[1,1] = 3·6 + 4·8 = 50
```

每个 `C[i,j]` 是 A 的第 i 行与 B 的第 j 列的点积。关键观察：**A 的同一行被多个输出列复用，B 的同一列被多个输出行复用**。如果每个输出都独立从全局内存读整行整列，复用就浪费了——这正是分块的动机。

## 8.2 分块的三层结构

本课 kernel 把输出切成 16×16 的 tile，每个线程组负责一个输出 tile：

```text
for ko in K 维的每个 32 宽小段:
    T.copy(A[by*16, ko*32], As)   # A 的 16×32 块 → shared
    T.copy(B[ko*32, bx*16], Bs)   # B 的 32×16 块 → shared
    T.gemm(As, Bs, Cl)            # 16×32 @ 32×16 累加进 fragment
T.copy(Cl, C[by*16, bx*16])       # 累加器 → 全局输出
```

- `As/Bs` 在 shared：块内数据被组内线程反复使用，放快存储；
- `Cl` 是 fragment 累加器：`T.gemm` 默认**累加**（`clear_accum=False`），所以 K 循环前 `T.clear(Cl)` 一次，循环里不断累加；
- `T.gemm` 是 tile 级原语：你声明“这两块相乘累加到那块”，编译器选择具体指令。本机 0.1.15 的 Metal 管线会把 fragment 累加器映射到 SIMD-group 矩阵路径（安装源码 `metal/pipeline.py` 与 `metal_macro_generator.py` 可见）——**不要把它当成普通标量循环**，也不要假设所有后端走同一条指令路径。

## 8.4 非整除形状：主机补零 + 裁剪

kernel 要求 M、N 是 16 的倍数、K 是 32 的倍数。`matmul()` 包装函数在主机侧：

1. 把 A 补零到 `(ceil(M/16)*16, ceil(K/32)*32)`，B 同理；
2. 运行 kernel；
3. 裁剪回 `(M, N)`。

补零不改变数学结果：多出来的行/列全是 0，点积贡献为 0。这是第 6 课补零策略在二维的推广。**代价**是算了无用功——形状越不整除浪费越多；实战篇会讨论设备端边界处理等替代方案。

## 8.5 改一个条件

把 `TILE` 从 16 改成 32（同时改包装函数的倍数检查），复跑 16×16×32 用例：结果应不变，但每组工作量变大。**不要据此断言谁更快**——本课没计时；第 11 章有 tile=64 反而慢 46 倍的真实负面结果，说明“块越大越好”是错觉。

## 8.6 练习与自检

1. 为什么 `T.clear(Cl)` 放在 K 循环外而不是循环内？
2. `T.copy(A[by*16, ko*32], As)` 搬的是多大的块？两个维度各由谁决定？
3. 3×5×7 的输入补零后实际算了多大的矩阵乘？浪费比例大约多少？

<details>
<summary>参考答案</summary>

1. 循环内 clear 会把上一段的累加结果清掉，最终只剩最后一段的贡献。
2. 16×32；行宽 16 由 `As` 形状决定，列宽 32 由 `As` 第二维决定，源表达式只给首地址。
3. 补到 16×32×16（M→16, N→16, K→32），有效计算 3·5·7=105 个乘加，实际 16·16·32=8192 个，约 98.7% 是补零浪费——小形状下分块开销显著，这正是教学例与性能例的区别。

</details>

**本课带走：** 输出 tile + K 维分块 + shared 暂存 + fragment 累加是矩阵乘的标准骨架；`T.gemm` 是声明式 tile 原语；补零让固定 tile 形状适配任意输入。下一课看怎样把两个 kernel 合成一个。
